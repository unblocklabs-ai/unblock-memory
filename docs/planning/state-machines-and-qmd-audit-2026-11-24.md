# Part 1 — `@unblocklabs/qmd` Dependency & Integration Friction

## TL;DR

`unblock-memory` barely uses `@unblocklabs/qmd`'s high-level SDK (`store.search`, `searchLex`, `searchVector`, `expandQuery`, `multiGet`, `addCollection`, `removeCollection`, contexts, and QMD's TypeSafe client are **all unused**). Instead, it uses QMD as a low-level BM25/vector engine and reaches straight into `store.internal.db`, `store.internal.llm`, and `store.internal.*` across **7 modules**, while carrying several heavy/stale QMD transitive dependencies.

Because you own `@unblocklabs/qmd`, **6 small QMD-side API additions + 1 cleanup** would delete hundreds of lines of fragile glue, monkey-patches, and raw SQL in `unblock-memory`.

---

## Friction Points & Simplifications

### 1. Massive `store.internal.db` schema coupling (7 modules, 6 private QMD tables)
- **Where:** [manager.ts](../../src/manager.ts#L205-L252), [manager.ts](../../src/manager.ts#L522-L541), [manager.ts](../../src/manager.ts#L845-L952), [training-retrieval.ts](../../src/training-retrieval.ts#L82-L86), [quality-audit.ts](../../src/quality-audit.ts#L68-L79), [analysis.ts](../../src/analysis.ts#L218-L489), [evidence-review.ts](../../src/evidence-review.ts#L26-L46), [cluster-review.ts](../../src/cluster-review.ts#L9-L10), [response-memory.ts](../../src/response-memory.ts#L17-L20).
- **Friction:** `unblock-memory` writes raw SQL against QMD's internal tables (`documents`, `content`, `content_vectors`, `vectors_vec`, `documents_fts`, `store_config`), and in **three places duplicates logic QMD already built**:
  1. `cleanupRemovedDocuments` ([manager.ts:L217-L230](../../src/manager.ts#L217-L230)) manually calls `deleteInactiveDocuments()`, `cleanupOrphanedVectors()`, `cleanupOrphanedContent()`, `INSERT INTO documents_fts...('optimize')`, `vacuumDatabase()`, and `PRAGMA wal_checkpoint(TRUNCATE)` — even though `@unblocklabs/qmd` already exports `Maintenance` ([maintenance.d.ts](../../node_modules/@unblocklabs/qmd/dist/maintenance.d.ts#L9-L33)) implementing all of those except `secure_delete` and `wal_checkpoint(TRUNCATE)`.
  2. `ensureSemanticChunking` ([manager.ts:L205-L211](../../src/manager.ts#L205-L211)) queries `store_config` directly even though QMD already has `getEmbeddingChunkStrategy(db)` ([store.d.ts:L213](../../node_modules/@unblocklabs/qmd/dist/store.d.ts#L213)), just not exposed on `QMDStore`.
  3. [training-retrieval.ts:L66-L86](../../src/training-retrieval.ts#L66-L86) uses `createRequire(import.meta.resolve("@unblocklabs/qmd"))` to smuggle QMD's transitive `better-sqlite3` and `sqlite-vec` native bindings and join `documents + content + content_vectors + vectors_vec` — even though QMD **already has** `exportEmbeddedSnapshot(store, { collections })` ([embedded-snapshot.d.ts](../../node_modules/@unblocklabs/qmd/dist/embedded-snapshot.d.ts#L40-L44)) specifically designed to hide QMD's SQLite schema, just not re-exported from `dist/index.d.ts`!
- **Simplification in QMD:**
  - Add `secureDelete?: boolean` + `walCheckpoint?: boolean` to `Maintenance.run()` / `QMDStore.cleanup()` and expose `store.getChunkStrategy()` + `store.purgeCollection(name)`.
  - Re-export `exportEmbeddedSnapshot` (or a read-only `readEmbeddedSnapshot(dbPath, { collections })` helper) from `@unblocklabs/qmd` root so `training-retrieval.ts` stops smuggling `better-sqlite3`/`sqlite-vec`.

### 2. Fake filesystem collection & `store.internal` bypass for virtual documents
- **Where:** [manager.ts:L516-L518](../../src/manager.ts#L516-L518), [extraction-index.ts:L24-L41](../../src/extraction-index.ts#L24-L41).
- **Friction:** Because QMD only registers filesystem-backed collections, extracted memories register a dummy glob `{ path: dirname(this.#dbPath), pattern: ".no-extracted-files", includeByDefault: false }` so `update()` skips it, then bypass the SDK via `internal.getActiveDocumentPaths / deactivateDocument / findActiveDocument / insertContent / insertDocument`.
- **Simplification in QMD:** Support first-class virtual collections (`{ virtual: true, includeByDefault: false }`) with `store.syncVirtualDocuments(collection, docs)` (or `upsertDocument` / `deactivateDocument`) on `QMDStore`.

### 3. Monkey-patching `qmd.internal.searchVec` & external `#operationChain` serialization
- **Where:** [training-retrieval.ts:L148-L176](../../src/training-retrieval.ts#L148-L176), [manager.ts:L350-L360](../../src/manager.ts#L350-L360), [manager.ts:L1038-L1068](../../src/manager.ts#L1038-L1068).
- **Friction:** QMD does not serialize concurrent native `node-llama-cpp` vector/embedding calls on a single warm context. As a result:
  - `training-retrieval.ts` creates an in-memory store, **monkey-patches `qmd.internal.searchVec`** with a promise tail, directly writes `store_config`, calls `ensureVecTable / insertContent / insertDocument / insertEmbedding`, and copies `Buffer` → `Float32Array` manually.
  - `manager.ts` wraps every QMD call in `#operationChain` (which also leaks into shutdown/read races — see Part 2).
- **Simplification in QMD:** Serialize native embedding/vector context access *inside* QMD's `LlamaCpp` / `Store`, and add an in-memory snapshot constructor `createMemoryStore({ documents, vectors, chunkStrategy })` (inverse of `exportEmbeddedSnapshot`). That deletes ~60 lines of fragile monkey-patching in `training-retrieval.ts`.

### 4. Reaching into `store.internal.llm` just for embeddings & token counting
- **Where:** [manager.ts:L1085](../../src/manager.ts#L1085), [manager.ts:L1151-L1186](../../src/manager.ts#L1151-L1186).
- **Friction:** Skill Whisperer grabs `store.internal.llm`, imports `formatDocForEmbedding`/`formatQueryForEmbedding`, and hand-rolls `cosineSimilarity` just to embed skill descriptions on QMD's already-warm model. `#renderSearchHits` grabs `store.internal.llm` solely for token counting during session passage expansion.
- **Simplification in QMD:** Expose `store.embedDocuments(docs)` / `store.embedQuery(text)` (or `store.rankTexts(query, docs)`) and `store.countTokens(text)` on `QMDStore`. Zero `store.internal.llm` casts needed.

### 5. Dual SQLite drivers (`better-sqlite3` vs `node:sqlite`) & co-mingled `index.sqlite`
- **Where:** [response-memory.ts:L13-L20](../../src/response-memory.ts#L13-L20), [training-retrieval.ts:L66-L68](../../src/training-retrieval.ts#L66-L68), [manager.ts:L523-L540](../../src/manager.ts#L523-L540).
- **Friction:** `unblock-memory` uses Node 22's built-in `node:sqlite` everywhere — including opening QMD's `index.sqlite` directly for FTS5 in `response-memory.ts` — while QMD uses native `better-sqlite3` + `sqlite-vec`. Meanwhile, `memory_analysis_*` and `memory_curation` tables live *inside* QMD's `index.sqlite`, coupling QMD cleanup/VACUUM with `unblock-memory`'s cluster staleness.
- **Simplification:** Long-term, migrating QMD onto `node:sqlite` (once `loadExtension` with `sqlite-vec` is verified across macOS/Linux) removes the native `better-sqlite3` build dependency entirely. Short-term, exposing `store.searchWholeDocsLex(...)` or a read-only FTS helper avoids `response-memory.ts` bypassing QMD with raw `documents_fts` SQL.

### 6. Unused / stale QMD surface area & heavy transitive dependencies
- **Stale TypeSafe/Jev client inside QMD:** [typesafe-query.js](../../node_modules/@unblocklabs/qmd/dist/typesafe-query.js#L4-L75) still hardcodes `https://api.typesafe.ai/v1/systemone`, `jev-1.13.0`, `TYPESAFE_API_KEY`, and `TYPESAFE_API_KEY_FILE` (plus `zod`). `unblock-memory` never calls `store.search()`, so it never runs this path — **but** any standalone `qmd` CLI/MCP use will still hit legacy TypeSafe/Jev unless QMD is updated or that code is split out!
- **Unused transitive dependencies pulled into every OpenClaw install:** `package.json` of `@unblocklabs/qmd` unconditionally pulls in `@modelcontextprotocol/server`, 5 `tree-sitter-*` grammars + `web-tree-sitter`, `yaml`, and `zod` — none of which `unblock-memory` calls (`unblock-memory` only indexes Markdown/sessions and validates with `typebox`). Splitting `@unblocklabs/qmd-core` (engine + embeddings + SQLite) from CLI/MCP/TypeSafe/code-AST extras would dramatically shrink install footprint and native build failures.
- **Local install drift catch:** `package.json` and `package-lock.json` pin `"@unblocklabs/qmd": "3.0.4"`, while `node_modules/@unblocklabs/qmd/package.json` on disk is currently `3.0.2` (worth running `npm ci` / `npm install` when convenient).

# Part 2 — Implicit State Machines Audit (GPT-6.2 Sol, `high` effort)

Audited **`index.ts`, all 103 files under `src/`, and all 10 files under `scripts/`** in the current working tree (strictly read-only, source-derived interleavings).

## Top 5 Fix-First Invariant Traps

1. **Dossier approval can bless the wrong revision.** The update tool commits the dossier, rereads the *latest* change ID, then records verification. A competing write in that gap can receive the first writer's approval. The prompt hook also reads the dossier body and verifies the latest revision separately. Bind both writes and reads to the exact reviewed revision.
2. **Response audit can strand People Learning.** A failed memory assessment can be saved under an episode marked `ok`. The scheduler won't retry that episode, but People Learning counts it as unresolved. Give the memory stage independent retry eligibility.
3. **Inside Out can undo a purge.** An in-flight retry can overwrite a `Purged by operator` grade with `INSERT OR REPLACE`. A baseline refresh can also certify changes it never processed by hashing the database *after* the pass. Fence grade writes against tombstones and certify the inputs actually processed.
4. **Training can export targets from missing evidence.** With an existing index but no session manifest, both retrieval lanes can report empty hits, score zero, select winners, and export them. Separately, a failed retrieval tied to an old corpus can block evaluation before the repaired corpus is even inspected.
5. **Session sync has status without durable ownership.** Its lock is process-local; the persisted `pid` is not checked. Another process can mark a live run interrupted or start a competing sync. The projection/index/manifest pipeline also needs a completion proof tied to the exact inputs it processed.

**Leverage legend:** **High** = make the lifecycle explicit and fence its transitions; **Medium** = tighten invariants or centralize transitions; **Low** = keep the existing structure.
